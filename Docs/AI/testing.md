# Автотесты

Цель теста — подтвердить наблюдаемое поведение и сохранить безопасный рефакторинг. Тест не проверяет private-детали, порядок внутренних вызовов без контрактной причины или текущую структуру классов.

## Когда применять TDD

Для нового правила Domain/Application, state machine, расчёта, перехода состояния или исправления бага сначала написать падающий тест ожидаемого поведения, затем минимальную реализацию и только после этого рефакторить. Это рабочий TDD-цикл: red → green → refactor.

Не применять TDD механически к prefab wiring, сериализованным полям, анимации, input и Unity callback. Для них сначала выделить в pure C# проверяемое решение, если оно действительно есть; Unity-часть подтвердить сфокусированным PlayMode-тестом или ручным smoke-прохождением.

## Выбор уровня теста

| Что меняется | Автопроверка | Дополнительное подтверждение |
| --- | --- | --- |
| Domain/Application: правила, use case, state machine | Детерминированный EditMode-тест | Компиляция затронутых assembly |
| MVP/MVVM без prefab и serialized wiring | EditMode-тест Model/Presenter/ViewModel через публичный контракт | Компиляция |
| Root, DI, async, `Dispose`, cancellation | EditMode lifecycle-тест | Компиляция |
| Prefab, сцена, input, animation, serialized field | Минимальный PlayMode-тест, если сценарий автоматизируем | Unity manual smoke |
| Addressables или загрузка сцены | Тест handle/lifecycle | Unity manual smoke |

Зелёная компиляция не доказывает prefab, сцену, input или lifecycle Unity.

## Расположение и границы

Тесты располагаются рядом с feature:

```text
<Feature>/
  Tests/
    EditMode/
      Domain/
      Application/
      Runtime/
    PlayMode/
```

Тестовая asmdef ссылается только на проверяемый слой и нужные test dependencies. Для доступа к осознанно внутреннему pure C# контракту допустим точечный `InternalsVisibleTo` тестовой assembly; не делать API public только ради теста.

В Domain/Application не использовать `MonoBehaviour`, `Transform`, `GameObject`, статическое Unity-состояние или данные сцены. Unity bindings и lifecycle остаются во View/adapters. Не создавать интерфейс, DI-container или отдельный слой только ради теста маленького scene-bound кода.

## MVP и MVVM

Presenter и ViewModel тестируются через Base-контракты своей presentation-семьи. Если нужна подмена зависимости, использовать маленькую fake-реализацию, которая отражает поведение контракта, а не mock, повторяющий внутреннюю реализацию. Для Base-контракта на `MonoBehaviour` fake создаётся на test `GameObject` в EditMode; prefab wiring этим тестом не считается проверенным.

Проверять: результат команды/сценария, опубликованное состояние, реакцию на событие и освобождение подписок. Для lifecycle дополнительно проверять однократность `Initialize`, cancellation операций и освобождение child ровно один раз, включая порядок, когда он является контрактом.

## Правила читаемости

- Один тест — один сценарий и одна причина падения.
- Имя: `<Действие>_<Условие>_<ОжидаемыйРезультат>`.
- Использовать локальные Arrange/Act/Assert и явные тестовые данные; не скрывать важную настройку в общем fixture.
- Проверять публичный эффект, а не private-поля, reflection или число технических вызовов.
- Общий fixture/factory допустим только для повторяющихся осмысленных defaults; конкретные значения сценария задаются в самом тесте.
- При исправлении дефекта сначала добавить регрессионный тест, воспроизводящий поведение пользователя.
