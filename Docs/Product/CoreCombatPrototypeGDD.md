## 1. Назначение, иерархия и правила изменения

### 1.1. Назначение

Этот документ однозначно описывает, что должно быть собрано и проверено в первом playable-срезе DungeonTeam: **Stage 0 Core Combat Prototype**.

GDD отвечает на вопросы:

- какое наблюдаемое поведение требуется от лидера, спутников, команд, врагов и encounter;
- какие условия делают сравнительный тест вариантов управления честным;
- какие данные и проверки нужны для решения `proceed / iterate / reduce scope / pivot / stop`;
- какие границы ответственности должны пережить прототип, если core подтвердится;
- какие решения обязаны остаться дешёво заменяемыми, если гипотеза не подтвердится.

Документ не является class design, техническим заданием на конкретные Unity-компоненты или планом production всей игры.

### 1.2. Место в иерархии

При конфликте действует следующий приоритет:

1. `ProductDirection.md`;
2. `ExperienceDirection.md`;
3. `ProductValidationPlan.md`;
4. этот GDD для исполняемых правил Stage 0;
5. будущий technical design и backlog реализации.

`PublisherVerticalSliceBrief.md` описывает Stage 2 и не может расширять Stage 0. Если Stage 2 требует элемент, который не нужен центральной гипотезе Stage 0, этот элемент остаётся за пределами текущего среза.

### 1.3. Классы решений

Каждое существенное решение в GDD относится к одному из четырёх классов:

| Метка | Класс | Значение |
| --- | --- | --- |
| **[C] Contract** | стабильный продуктовый контракт | Должен пережить Stage 0 и направлять Stage 1, если не изменён вышестоящий продуктовый документ |
| **[H] Hypothesis** | рабочая гипотеза | Проверяется Stage 0; может быть изменена по данным без переписывания всего core |
| **[P] Proxy** | временное решение | Нужно только для честного и читаемого теста; не считается обещанием production-реализации |
| **[D] Deferred** | отложенное решение | Намеренно не проектируется до следующего gate |

Отсутствие метки у конкретного tuning-параметра означает, что он настраиваемый и не является продуктовым контрактом.

### 1.4. Нормативные слова

- **Должно / запрещено** — обязательное условие Stage 0.
- **Следует** — рекомендуемое решение; отклонение фиксируется в technical design или decision report.
- **Может** — допустимый вариант, не обязательный scope.

### 1.5. Change control

До начала внешнего comparative test фиксируются:

- версия GDD;
- build ID;
- варианты A и B;
- tuning profile;
- encounter seed/сценарий;
- target device и экран;
- известные дефекты;
- критерии исключения сессии.

После просмотра результатов нельзя задним числом менять пороги или трактовку событий. Изменение центральной гипотезы, состава вариантов или продуктового контракта требует:

1. описать полученные данные;
2. указать, что именно меняется и почему;
3. проверить связанные продуктовые документы;
4. выпустить новую версию GDD;
5. считать следующий прогон новым тестом.

## 2. Цель Stage 0 и центральная гипотеза

### 2.1. Цель

**[C]** Stage 0 должен доказать или опровергнуть, что прямое управление лидером и короткое влияние на автономный отряд интересны сами по себе в mobile-first action combat.

Это:

- не publisher vertical slice;
- не expedition prototype;
- не демо полной продуктовой петли;
- не production-ready combat platform;
- не повод заранее строить Stage 1+ системы.

### 2.2. Центральная гипотеза

> **[H] Прямо управляя одним лидером и влияя короткой командой на до трёх автономных спутников, игрок чувствует себя лидером живого отряда, замечает вклад разных ролей и хочет повторить бой с другим составом или моделью командования.**

### 2.3. Обязательные вопросы Stage 0

Срез обязан дать данные по каждому вопросу:

1. Осваивается ли landscape touch-управление без устного объяснения?
2. Оставляет ли auto basic attack игроку содержательные решения или делает бой пассивным?
3. Читаются ли лидер, три роли, намерения спутников и ключевые угрозы на минимальном целевом экране?
4. Воспринимается ли автономность как полезность, а не потеря контроля?
5. Может ли игрок объяснить, как его команда изменила поведение отряда?
6. Чем отличаются Rally и контекстная команда по влиянию, понятности, нагрузке и доверию?
7. Можно ли атрибутировать успех и провал решениям игрока, понятной угрозе или конкретному действию спутника?
8. Достижимы ли читаемость и ориентир производительности на выбранном Android device?
9. Можно ли расширять роли, feedback и encounter без сценовых исключений и глобальных менеджеров?
10. Какое следующее решение оправдано данными: выбрать вариант, повторить тест, сократить группу, изменить control/party model или остановить расширение?

### 2.4. Принцип достаточности

Каждый in-scope элемент должен поддерживать хотя бы один вопрос выше. Если элемент нельзя связать с центральной гипотезой, fairness A/B, наблюдаемостью или feasibility gate, он не входит в Stage 0.

## 3. Связь с full vision

### 3.1. Контракты, которые должны пережить Stage 0

| Контракт | Требование Stage 0 | Почему сохраняется |
| --- | --- | --- |
| **[C] Landscape mobile-first** | Бой проектируется и проверяется на Android в landscape | Это зафиксированное направление продукта |
| **[C] Один прямо управляемый лидер** | Игрок не переключает прямой контроль на спутников | Сохраняет fantasy лидера, а не RTS/hero switching |
| **[C] Автономные role-driven спутники** | Спутники полезны без приказа на каждое действие | Основа отличимости продукта |
| **[C] Короткое лидерское влияние** | Команда меняет намерение группы без четырёх action bars | Поддерживает `Lead, don’t micromanage` |
| **[C] Auto basic attack** | Базовая атака лидера автоматизирована | Освобождает touch/input budget |
| **[C] Читаемая причинность** | Намерение, действие и результат видимы | Необходима для доверия к AI |
| **[C] Сменность control model** | Команда поступает в combat через явное намерение, а не зашита в роли/врагов | Позволяет честный pivot после Stage 0 |
| **[C] События и данные поведения** | Команды, действия, урон, провалы и performance наблюдаемы | Позволяет сравнение и развитие без переписывания core |
| **[C] Feature ownership** | Encounter имеет явного владельца lifecycle и состояния | Предотвращает одноразовый сценовый прототип |

### 3.2. Рабочие гипотезы среза

- **[H]** Состав «лидер + три спутника» остаётся читаемым на телефоне.
- **[H]** Фиксированная или мягко следующая камера 3/4 достаточна без ручного вращения.
- **[H]** Одной активной способности, уклонения, target priority и одной командной зоны достаточно для активного боя.
- **[H]** Rally и контекстная команда являются достаточными кандидатами для выбора направления.
- **[H]** Один encounter длительностью примерно 3–5 минут даёт достаточно ситуаций для оценки лидерства.
- **[H]** Три proxy-роли достаточно различимы без production art и narrative.

### 3.3. Временные proxy-решения

- **[P]** Graybox arena, proxy-модели, простые материалы, короткие сигналы и placeholder audio.
- **[P]** Один фиксированный состав и один набор угроз для первичного A/B; другой состав может использоваться только для replay-intent проверки, если он не расширяет core.
- **[P]** Простая health/damage модель без production progression, equipment и экономики.
- **[P]** Combat incapacity спутника без травм, памяти, permadeath или восстановления в хабе.
- **[P]** Локальные файлы телеметрии без analytics SDK, backend и аккаунта.
- **[P]** Служебный экран выбора варианта, seed, reset и replay.
- **[P]** Editor input adapter с теми же намерениями, что и touch, только для скорости разработки.

### 3.4. Намеренно отложено

**[D]** До Stage 1+ не фиксируются:

- структура экспедиции, данжа и комнат;
- контракты, маршруты и push-your-luck;
- хаб и post-run consequence;
- loot, economy, equipment и progression;
- roster management и выбор состава как полноценная система;
- relationships, memory, traits, injuries и permadeath;
- narrative delivery и production character writing;
- monetization, stamina, store и live ops;
- backend, account, cloud save, online/co-op;
- production content counts, final art и content pipeline;
- business model, PC/console scope и 1.0/endgame.

Граница Stage 0 должна позволять добавить эти системы позже через отдельные контракты, но не содержать их заготовки «на будущее».

## 4. Целевой player experience

### 4.1. Фантазия среза

Игрок входит в опасную арену как мобильный полевой лидер. Он лично перемещается, уклоняется, выбирает приоритет и применяет активное умение. Рядом действуют три самостоятельных бойца. В спокойной ситуации они компетентны без команды; под давлением короткая команда игрока заметно меняет их общий ответ.

### 4.2. Эмоциональная дуга 3–5 минут

> быстрое освоение → первая уверенность в собственной мобильности → замеченная полезность спутника → одновременные угрозы → лидерская команда → читаемый перелом ситуации → объяснимый успех или провал → желание сравнить другой подход

### 4.3. Moment-to-moment loop

1. Считать положение лидера, отряда и ключевой угрозы.
2. Переместиться или уклониться от телеграфа.
3. Подтвердить или сменить priority target.
4. Использовать активную способность в подходящий момент.
5. При необходимости задать группе намерение.
6. Увидеть подтверждение команды и role-specific реакцию.
7. Оценить результат и следующий риск в encounter.

### 4.4. Критические наблюдаемые моменты

За одну валидную сессию должны иметь возможность естественно возникнуть:

- спутник самостоятельно предотвращает или уменьшает понятную угрозу;
- игрок командой меняет приоритет, строй или темп отряда;
- разные роли отвечают на одну ситуацию различимыми действиями;
- игрок избегает угрозы движением/уклонением, а не только выдерживает урон;
- провал связывается с читаемой причиной.

Эти моменты подготавливаются encounter design, но не запускаются как гарантированный showcase-скрипт.

## 5. Scope и non-goals

### 5.1. Полный in-scope

Stage 0 включает:

- один управляемый лидер;
- движение, auto basic attack, priority targeting, уклонение и одну active ability;
- до трёх автономных proxy-спутников;
- роли `protector`, `damage/debuffer`, `support/controller`;
- общую минимальную combat model;
- один небольшой набор функционально разных врагов и угроз;
- одну graybox-арену;
- один составной encounter примерно на 3–5 минут;
- control variant A — Rally;
- control variant B — context command;
- минимальный touch HUD и readability feedback;
- camera 3/4 без обязательного ручного вращения;
- победу, поражение, pause/focus recovery, reset и replay;
- служебный выбор A/B до старта попытки;
- локальную telemetry и performance samples;
- Editor adapter для удобства разработки;
- Android build как основной proof path;
- internal usability, counterbalanced A/B и external blind comparative playtest;
- decision report.

### 5.2. Non-goals

В Stage 0 явно не входят:

- dungeon generation, rooms и room grammar;
- exploration, route choice и traps как системы экспедиции;
- contracts, optional objectives и extraction/return flow;
- push-your-luck и решение «продолжить/вернуться»;
- hub/guild;
- loot, rewards, inventory, equipment и economy;
- supplies и подготовка экспедиции;
- progression, meta и upgrades;
- полноценный roster/composition selection;
- relationships, memory, personality simulation, traits, injuries и permadeath;
- narrative, dialogue system и authored story content;
- monetization, gacha, store, stamina, battle pass и paid power;
- backend, accounts, cloud, telemetry service, online и multiplayer;
- saves вне минимального test harness;
- Addressables/content streaming и scene transition pipeline;
- production art, production animation set, cinematics и production audio;
- boss, biome, большой набор врагов или баланс всей игры;
- accessibility suite целиком; проверяется только критичная читаемость и отсутствие color-only сигналов;
- localization pipeline;
- PC/console controls как продуктовая поддержка;
- универсальная ability/status/AI/combat platform;
- asmdef, интерфейсы или сервисы, созданные только ради предполагаемого будущего использования.

### 5.3. Scope guard

Новый элемент может войти только если:

1. закрывает выявленный blocker центральной гипотезы;
2. не может быть проверен более дешёвым способом;
3. имеет явного владельца и критерий удаления;
4. добавлен в новую версию GDD до теста.

## 6. Камера, управление и input budget

### 6.1. Камера

**[H]** Базовый вариант — фиксированная или мягко следующая camera 3/4:

- камера удерживает лидера, основную часть отряда и ближайшие угрозы в читаемой области;
- ручное вращение не требуется;
- движение камеры не создаёт ложного направления touch-ввода;
- камера не меняет угол резко во время атаки, dodge или команды;
- временно разошедшиеся спутники обозначаются edge marker, если выходят из кадра;
- опасный телеграф не должен регулярно начинаться за пределами доступного обзора без предупреждения.

Конфигурируемыми гипотезами остаются:

- угол, высота и дистанция;
- offset по направлению движения/угрозы;
- follow smoothing и dead zone;
- допустимый zoom response;
- правила удержания отряда в кадре;
- минимальная видимая дистанция телеграфа.

Ручное вращение, pinch zoom и cinematic camera не добавляются без отдельного тестового вопроса.

### 6.2. Touch input budget

Постоянные зоны боя:

| Зона | Действие | Правило |
| --- | --- | --- |
| Слева | виртуальный joystick | Непрерывное движение лидера |
| Справа | dodge | Одно дискретное защитное действие |
| Справа | active ability | Одно дискретное активное решение лидера |
| Справа | command | Одна постоянная command-зона; поведение зависит от A/B |
| Поле/минимальный target control | priority target | Не требует отдельной панели целей |

Ограничения:

- basic attack не получает отдельную кнопку;
- одна функция не должна требовать точного нажатия по маленькому world-space объекту;
- критические кнопки не перекрывают телеграфы и не конфликтуют с системными жестами;
- одно нажатие не может незаметно означать разные действия: прогнозируемый контекст показывается до активации;
- удержание, double tap и swipe используются только после отдельной usability-проверки;
- размер и расположение touch-зон являются гипотезами и проверяются на target device.

### 6.3. Priority target input

**[H]** Игрок должен иметь простой способ назначить или сменить приоритетную цель. Допустимые кандидаты реализации проверяются отдельно в internal usability:

- tap по крупной targetable области;
- короткое target-cycle действие;
- контекстный выбор ближайшей цели в направлении ввода.

До comparative test выбирается один способ и одинаково используется в A и B. Target selection не должен давать одному варианту дополнительную скрытую возможность.

### 6.4. Editor parity

**[P]** Keyboard/mouse или gamepad в Editor — только development adapter.

Он обязан отправлять те же игровые намерения:

- `Move`;
- `SetPriorityTarget`;
- `Dodge`;
- `UseLeaderAbility`;
- `IssueSquadCommand`;
- `Pause`;
- служебные `Reset/VariantSelect` вне боевого input budget.

Editor adapter не является доказательством эргономики. Поведение, зависящее от hover, точного mouse aim, дополнительных hotkeys или количества клавиш, запрещено переносить в продуктовую оценку.

## 7. Правила лидера

### 7.1. Движение

**[C]** Игрок напрямую и непрерывно управляет перемещением лидера по walkable area.

Требования:

- направление соответствует экранному/camera-relative вводу и не меняется неожиданно;
- отпускание joystick прекращает намеренное движение без заметного «доскальзывания», кроме явно читаемой анимационной инерции;
- auto attack и target selection не забирают движение;
- столкновение с препятствием не вызывает длительного застревания;
- лидер не выходит за combat bounds;
- hit reaction не лишает управления дольше, чем необходимо для читаемой обратной связи.

Скорость, acceleration, rotation speed и assist остаются tuning-параметрами.

### 7.2. Priority targeting

Цель считается валидной, если она:

- активна и уязвима;
- находится в допустимой combat area;
- достижима атакой по правилам дальности/линии взаимодействия;
- не скрыта состоянием, которое игрок не может распознать.

Правила:

1. Явно выбранная priority target имеет приоритет над auto-selection, пока остаётся валидной.
2. Потеря валидности снимает target lock с видимым feedback.
3. Без priority target basic attack выбирает ближайшую разумную угрозу по детерминированному правилу.
4. Auto-selection не должен регулярно выбирать далёкую цель вместо непосредственной угрозы.
5. Смена цели видна маркером и не меняет команду задним числом.

Конкретная scoring formula — предмет technical design и deterministic tests, а не контракт GDD.

### 7.3. Auto basic attack

**[C]** Basic attack запускается автоматически при валидной цели и соблюдении условий атаки.

Обязательное поведение:

- атака не делает игру полностью пассивной: позиция, цель, dodge, active ability и command остаются значимыми;
- атака не ведёт лидера через опасность без движения игрока;
- attack cadence и hit result читаются;
- длинный animation lock не блокирует своевременный dodge без предварительно проверенной причины;
- при выходе цели из допустимых условий лидер не атакует пустоту длительно;
- урон привязан к понятному моменту попадания/разрешения, а не к скрытому таймеру.

Damage, cadence, range, aim assist и правила cancel — настраиваемые гипотезы.

### 7.4. Dodge

**[H]** Dodge — короткое направленное защитное действие, позволяющее ответить на телеграфированную угрозу.

Требования:

- направление берётся из актуального movement input; fallback без направления задаётся явно и одинаково во всех тестах;
- старт и завершение читаются;
- dodge имеет настраиваемое окно избегания урона или эквивалентное правило безопасного перемещения;
- cooldown/charges и возможность cancel настраиваются до freeze build;
- невозможный dodge даёт немедленный feedback;
- dodge не переносит через закрытые bounds и не оставляет лидера в invalid navigation state.

Точная invulnerability window не фиксируется до usability/balance test.

### 7.5. Active ability

**[P]** Лидер имеет одну простую активную способность, создающую пространственно-временное решение и не дублирующую команду.

Рабочая функция:

- направленное или area-действие;
- заметный impact по выбранной угрозе;
- damage и/или короткий interrupt/control;
- явные ready, targeting, execution и cooldown states.

Способность не должна:

- автоматически решать все command-ситуации;
- требовать production status framework;
- создавать отдельное дерево улучшений;
- скрывать вклад спутников чрезмерным VFX.

Конкретная тема, величины и тип target acquisition — proxy/tuning.

### 7.6. Урон, состояние и смерть

- Лидер имеет видимое текущее и максимальное здоровье.
- Получение урона подтверждается world feedback и изменением состояния.
- Повторяющийся урон от hazard имеет понятную частоту или постоянный визуальный сигнал.
- На нуле здоровья лидер прекращает боевые действия и запускает defeat.
- **[P]** Спутник на нуле здоровья становится incapacitated до конца попытки; ручного revive в Stage 0 нет.
- Incapacitated спутник не считается активной целью, не продолжает действовать и остаётся визуально различимым от живого.
- Friendly fire отсутствует.
- Permanent death, injuries и post-run consequence отсутствуют.

### 7.7. Feedback лидера

Игрок должен различать:

- кого лидер считает priority target;
- когда basic attack попал или не состоялся;
- готовность/неготовность dodge и ability;
- входящий урон и его направление/источник, когда это важно;
- признание командой выданного намерения;
- смерть/недееспособность и причину defeat.

## 8. Общая боевая модель

### 8.1. Минимальные сущности правил

Для честного теста достаточно следующих понятий:

- combat actor;
- team/faction;
- position и валидная navigation area;
- current/max health;
- action intent;
- action lifecycle: `requested → started → resolved/cancelled`;
- target и target validity;
- damage instance с source/action attribution;
- threat telegraph;
- короткий control/debuff как часть конкретного proxy-действия;
- combat state и encounter phase.

Это логические данные поведения, а не обязательные классы или универсальный framework.

### 8.2. Время и разрешение действий

- Бой идёт в real time.
- Важные действия имеют различимые anticipation, active/resolution и recovery.
- Урон или control не применяются до читаемого окна действия, кроме заранее понятного contact damage.
- Одно событие урона имеет один основной source/action для telemetry.
- Одновременные эффекты разрешаются детерминированно по правилам technical design.
- Критически полезное действие спутника не зависит от скрытого случайного броска.

### 8.3. Пространственные правила

- Все боевые участники действуют в одной ограниченной 3D arena.
- Walkable и blocked зоны визуально различимы в graybox.
- Actor не должен системно перекрывать другого actor так, что теряется target/telegraph readability.
- Обход препятствий допускается; телепортация к строю запрещена, кроме явно помеченного recovery proxy после navigation failure.
- Если recovery proxy необходим, событие логируется и исключается из оценки естественности AI.

### 8.4. Справедливость

Ситуация считается справедливой, если:

- угроза была видима или заранее обозначена;
- у игрока/отряда существовала доступная контригра;
- команда имела предсказуемый результат или видимую причину отказа;
- урон и провал можно связать с источником;
- технический сбой не трактуется как игровая ошибка.

### 8.5. Что намеренно отсутствует

Нет production-правил:

- armor/resistance matrix;
- elemental system;
- stacking statuses и dispel;
- aggro/threat table общего назначения;
- resource economy;
- critical hit/random proc;
- combo tree;
- progression scaling;
- difficulty modes;
- loot drops.

Если конкретной роли или врагу нужен debuff/control, он реализует только минимальную наблюдаемую семантику текущего encounter.

## 9. Спутники

### 9.1. Общие требования

**[C]** Спутники:

- действуют автономно без команды на каждую атаку;
- имеют различимые role duties;
- реагируют на команду через свою роль, а не одинаковой копией действия;
- сообщают важное намерение до результата;
- не саботируют ясную команду;
- не покидают тактическую и визуальную связь с отрядом без причины;
- не используют скрытые правила, которые невозможно объяснить игроку.

### 9.2. Роли

| Роль | Основная обязанность | Автономное ключевое действие | Вклад в команду |
| --- | --- | --- | --- |
| **Protector** | Снижать давление на лидера/уязвимого союзника и удерживать пространство | Перехватить читаемую угрозу, коротко блокировать/оттеснить или занять защитную позицию | Создаёт безопасное окно и стабилизирует строй |
| **Damage/Debuffer** | Быстро превращать priority target в уязвимую или сокращать её время жизни | Нанести заметный burst или наложить один читаемый debuff | Усиливает общий focus и завершает опасную цель |
| **Support/Controller** | Менять темп боя, спасать состояние или ограничивать опасную зону/врага | Короткое лечение/mitigation либо control по понятному trigger | Даёт время перегруппироваться или реализовать давление |

Точная способность каждой роли — **[P]**, но её функция и наблюдаемая причинность обязательны.

Каждая роль должна иметь минимум одну наблюдаемую синергию с другой ролью: например, безопасное окно protector позволяет реализовать burst, а control support удерживает priority target под debuff. Для этого не создаётся универсальная combo-система; достаточно причинно связанного поведения текущих proxy-действий.

### 9.3. Порядок принятия решений

Рабочий приоритет AI:

1. Проверить валидность actor/state/navigation.
2. Не входить намеренно в очевидную смертельную угрозу, если нет role-specific причины.
3. Выполнить активную принятую команду в пределах её срока и условий.
4. Выполнить emergency role duty, если промедление делает действие бессмысленным.
5. Выполнить основную role duty.
6. Восстановить допустимую связь/дистанцию с группой.
7. Выполнять basic offense по предсказуемому target rule.

Конфликт пунктов 3 и 4 решается явно:

- emergency может прервать команду только для предотвращения немедленного incapacitation лидера/союзника;
- причина должна быть видима и записана как `command_override_reason`;
- частые override означают проблему дизайна, а не «умный AI».

### 9.4. Разрешённое поведение

Спутнику разрешено:

- выбирать role-appropriate позицию;
- временно отделяться для выполнения понятного действия;
- уклоняться/выходить из опасной зоны;
- менять локальную цель ради немедленной угрозы по правилам роли;
- откладывать действие, если target/path/action invalid, с видимым отказом;
- возвращаться к formation после завершения действия.

### 9.5. Запрещённое поведение

Спутнику запрещено:

- игнорировать принятую команду без причины;
- преследовать неважную цель за пределы допустимой squad distance;
- стоять в очевидном hazard при доступном выходе;
- блокировать движение лидера длительно;
- одновременно спорить за одну позицию с другими спутниками;
- использовать невидимый teleport как обычное перемещение;
- менять priority target группы скрыто;
- расходовать общий невидимый ресурс;
- отменять полезное действие ради косметической formation;
- маскировать navigation/logic bug как черту характера.

### 9.6. Telegraphing намерения

Для ключевого действия спутника обязательны минимум два канала, один из которых не зависит только от цвета:

- характерная поза/anticipation;
- movement line или заметное позиционирование;
- world marker/icon;
- короткая роль-специфичная реплика/звук;
- уникальный VFX формы;
- feedback результата на защищённой/поражённой цели.

Игрок должен иметь возможность связать:

> причина → намерение спутника → действие → результат.

### 9.7. Условия доверия игрока

Спутник считается заслуживающим доверия, если участник:

- правильно описывает его роль;
- может вспомнить хотя бы одно полезное автономное действие;
- понимает реакцию на команду;
- не объясняет ключевой провал несправедливым или случайным AI;
- видит причину невыполненной команды;
- не вынужден постоянно контролировать позицию спутника вручную.

## 10. Control variants

### 10.1. Общие правила честного сравнения

Оба варианта используют:

- одинакового лидера, спутников, врагов и arena;
- одинаковые health/damage/action budgets;
- одинаковый target selection;
- одну постоянную command-зону в HUD;
- одинаковый базовый cooldown budget;
- одинаковую доступность role actions;
- одинаковый encounter seed/order в рамках test protocol;
- одинаковый уровень visual/audio feedback;
- одинаковый onboarding budget.

Запрещено:

- усиливать врагов только против одного варианта;
- давать одному варианту эксклюзивную способность роли;
- писать encounter, который решается только заранее желаемой командой;
- компенсировать непонятный input скрытым auto-correction только в одном варианте;
- сравнивать polished A с placeholder B;
- менять tuning между участниками без нового build/config ID.

### 10.2. Variant A — Rally

#### Intent

**[H]** Rally передаёт группе единое намерение: синхронно ответить на текущий приоритет, сохраняя различия ролей.

#### Input

- Короткое нажатие command button.
- Если существует валидная priority target, Rally связывается с ней.
- Если priority target отсутствует, Rally связывается с лидером/его текущей позицией как с точкой сборки.
- Предстоящий тип `Rally on target` или `Rally on leader` показывается на кнопке/маркером до нажатия.

#### Role-specific response

При `Rally on target`:

| Роль | Ожидаемая реакция |
| --- | --- |
| Protector | Стабилизирует пространство между основной угрозой и лидером, создавая безопасное окно для общего давления |
| Damage/Debuffer | Приоритизирует цель и применяет доступный burst/debuff |
| Support/Controller | Ограничивает цель/окружение или поддерживает окно атаки, не дублируя damage-role |

При `Rally on leader`:

| Роль | Ожидаемая реакция |
| --- | --- |
| Protector | Возвращается в защитную позицию и перехватывает ближайшее давление |
| Damage/Debuffer | Разрывает опасное преследование и сохраняет pressure только в безопасном радиусе |
| Support/Controller | Стабилизирует группу лечением/mitigation/control по доступной необходимости |

#### Feedback

- Немедленное подтверждение input.
- Общий Rally marker на target/точке.
- Короткие role acknowledgements без трёх конкурирующих реплик.
- Отдельное начало и результат каждой role reaction.
- Явный feedback, если роль не может начать реакцию.

#### Ограничения

- Active window, cooldown, allowed radius и response latency — настраиваемые параметры.
- Новое Rally не должно создавать несколько конфликтующих intents.
- Повторное нажатие во время cooldown даёт feedback и не теряется молча.
- Rally не телепортирует спутников и не гарантирует неуязвимость.
- После завершения/отмены каждый спутник возвращается к автономному приоритету.

#### Edge cases

- Target умер до реакции: роль завершает уже валидное действие либо отменяет его с feedback; не выбирает новую скрытую общую цель.
- Target стал unreachable: Rally завершается для затронутой роли с причиной.
- Спутник incapacitated: он не отвечает; HUD не показывает ложное подтверждение.
- Спутник выполняет emergency save: override разрешён по правилам 9.3 и логируется.
- Лидер покинул Rally radius: реакция не должна вести отряд в бесконечное преследование.
- Pause/focus loss замораживает active window.

### 10.3. Variant B — Context Command

#### Intent

**[H]** Context Command даёт игроку более конкретное групповое намерение при том же постоянном command control. Контекст определяется детерминированно и виден до нажатия.

Минимальный набор:

- `Focus` — давление на priority target;
- `Regroup` — вернуться к лидеру и восстановить безопасную связь;
- `Protect` — защитить обозначенного угрожаемого участника.

Если internal usability покажет, что три контекста не читаются в touch budget, до freeze допускается минимальный эквивалент из двух контекстов. Это изменение фиксируется как новая версия варианта, а не скрытое упрощение.

#### Context resolution

До нажатия command button отображает будущую команду:

1. При валидной hostile priority target — `Focus`.
2. При явно обозначенной критической угрозе лидеру/союзнику — `Protect`.
3. При отсутствии двух контекстов выше — `Regroup`.

При конфликте UI показывает выбранный контекст до активации. Priority rule не меняется внутри frozen build.

#### Role-specific response

`Focus`:

| Роль | Ожидаемая реакция |
| --- | --- |
| Protector | Создаёт безопасный фронт относительно цели и удерживает помеху |
| Damage/Debuffer | Максимизирует доступное давление/debuff по цели |
| Support/Controller | Ограничивает контригру цели или поддерживает focus window |

`Regroup`:

| Роль | Ожидаемая реакция |
| --- | --- |
| Protector | Возвращается первым к защитной позиции |
| Damage/Debuffer | Прерывает дальнее преследование и возвращается в допустимый радиус |
| Support/Controller | Контролирует ближайшую угрозу или стабилизирует самого уязвимого при сборе |

`Protect`:

| Роль | Ожидаемая реакция |
| --- | --- |
| Protector | Приоритизирует перехват/mitigation угрозы обозначенному actor |
| Damage/Debuffer | Давит на источник угрозы, если он валиден |
| Support/Controller | Даёт защитный/контролирующий ответ обозначенному actor или источнику |

#### Feedback

- Иконка и world preview выбранного контекста до нажатия.
- Подтверждение названия команды после нажатия.
- Маркер target/protected actor/regroup point.
- Role acknowledgements и результаты того же качества, что у Rally.
- Если контекст изменился между intent preview и обработкой input, команда использует показанный на момент нажатия snapshot либо явно отклоняется; скрытая подмена запрещена.

#### Ограничения

- Context Command использует тот же общий cooldown/response budget, что Rally.
- Отдельные cooldown для `Focus/Regroup/Protect` не вводятся в Stage 0.
- Команда не выбирает за игрока новую hostile priority target.
- Context resolver не должен скрыто решать весь бой вместо игрока.

#### Edge cases

- Угрожаемый actor перестал быть валиден: `Protect` отменяется с feedback или завершается по уже начатому безопасному действию.
- Hostile target умер: `Focus` не перескакивает скрыто на другого врага.
- Squad уже собран: `Regroup` подтверждается коротко и не запускает лишнее движение.
- Несколько союзников под угрозой: deterministic resolver выбирает одного и показывает выбор до input.
- Context меняется быстро: применяется debounce/стабилизация как tuning, но preview остаётся правдивым.
- Pause/focus loss замораживает command state и cooldown.

### 10.4. Настраиваемые параметры обоих вариантов

До freeze build фиксируются в tuning profile:

- cooldown;
- active intent duration;
- command radius/validity;
- acknowledgement latency budget;
- role action availability;
- distance для regroup;
- target validity timeout;
- допустимый emergency override;
- интенсивность visual/audio/haptic feedback.

Точные значения не являются контрактом GDD. Любое различие между A и B должно иметь заранее записанную причину и не менять общий power budget.

### 10.5. Что сравнивается

Сравниваются:

- самостоятельное понимание input;
- число осмысленных и ошибочных применений;
- скорость от input до замеченной реакции;
- способность объяснить влияние;
- различимость role-specific response;
- доверие к автономности;
- workload и физическая нагрузка;
- результат encounter и failure attribution;
- субъективное чувство лидерства;
- предпочтение и причина предпочтения.

Win rate или DPS не выбирают победителя без качественного подтверждения.

## 11. Враги, угрозы, arena и encounter

### 11.1. Функция контента

Контент обязан различать качество:

- позиционирования;
- target priority;
- своевременного dodge/ability;
- наблюдения за спутниками;
- выбора момента и смысла команды.

Encounter не должен сводиться к проверке суммарного DPS или заранее требовать конкретный variant.

### 11.2. Минимальные архетипы угроз

| Архетип | Поведение | Проверяемое решение |
| --- | --- | --- |
| **Pressure melee** | Преследует и вытесняет лидера/отряд из удобной позиции | Движение, protector, regroup |
| **Telegraphed area threat** | Создаёт заметную область опасности с временем реакции | Camera/readability, dodge, spacing |
| **Priority disruptor** | Готовит усиление, дальнее давление или опасное действие, которое выгодно остановить | Target selection, focus, damage/debuffer/control |

Допускается один elite-модификатор существующего архетипа, только если он нужен кульминации и не требует новой системы.

### 11.3. Требования к врагам

- Силуэт и threat function различимы.
- Опасное действие телеграфируется не только цветом.
- Угроза имеет минимум одну контригру.
- Target choice объяснимо и не меняется хаотично.
- Враг не атакует из-за камеры без предупреждения.
- Смерть и прекращение угрозы читаются.
- Враги не имеют невидимых immunities и случайных one-shot.

### 11.4. Graybox arena

**[P]** Одна компактная arena содержит:

- читаемую внешнюю границу;
- основной открытый combat space;
- 2–3 препятствия/элемента геометрии, создающих pathing и spacing решения;
- минимум две оси подхода угроз;
- достаточно места для роли protector и regroup;
- фиксированные точки spawn, не появляющиеся непосредственно в слепой зоне игрока;
- безопасную start zone для первых секунд освоения;
- место для worst-case сочетания участников и телеграфов.

Размеры, форма, NavMesh и точное размещение — предмет graybox iteration. Арена не изображает комнату данжа и не создаёт route/exploration scope.

### 11.5. Encounter flow

Рабочая длительность — примерно 3–5 минут без onboarding и post-result.

| Фаза | Назначение | Содержание |
| --- | --- | --- |
| 0. Entry | Проверить ориентацию | Короткое безопасное окно: движение, отряд в кадре, доступные действия |
| 1. Single pressure | Показать базовую автономность | Один понятный pressure + возможность заметить ключевое действие спутника |
| 2. Competing priorities | Создать лидерское решение | Одновременно непосредственная и priority threat; нельзя оптимально решить только DPS |
| 3. Separation pressure | Проверить строй/сбор | Area threat или геометрия разводит позиции, оставляя честную контригру |
| 4. Crescendo | Проверить освоенные правила | Повторная комбинация знакомых угроз в worst-case readability/performance |
| 5. Resolution | Дать объяснимый итог | Победа или defeat, summary и быстрый replay |

Фазы могут идти по triggers, но:

- не подменяют AI заранее поставленным спектаклем;
- имеют одинаковые правила для A/B;
- не ждут бесконечно «правильной» команды;
- логируют начало/конец и причины перехода;
- не спавнят угрозу в нечитаемом состоянии.

### 11.6. Баланс честного теста

- Оба варианта должны иметь разумный путь к победе.
- Без команды encounter может быть завершён только с заметно большей сложностью/потерями, но не обязан быть невозможным.
- Команда должна влиять на outcome, а не давать гарантированную победу.
- Tuning избегает слишком быстрого убийства угроз до проявления ролей.
- Ошибка одного нажатия не должна без предупреждения завершать попытку.
- Контент и initial state воспроизводимы для сравнительных сессий.

## 12. HUD и readability budget

### 12.1. Информационные приоритеты

На минимальном целевом экране приоритет сигналов:

1. Немедленная телеграфированная угроза и безопасное направление.
2. Положение и состояние лидера.
3. Priority target и её критическое действие.
4. Активное squad intent и принятие команды.
5. Намерение/результат ключевого действия спутника.
6. Состояние отряда.
7. Готовность dodge, ability и command.
8. Служебная информация test harness.

Низший приоритет не может перекрывать высший.

### 12.2. Постоянный player HUD

Показывает только:

- здоровье лидера;
- компактное состояние трёх спутников;
- movement zone;
- dodge;
- active ability;
- command с preview текущего intent;
- priority target marker;
- pause.

Служебные variant/build/performance labels доступны в test overlay и не должны присутствовать в blind player view, кроме идентификатора, необходимого наблюдателю.

### 12.3. World feedback

Обязательны:

- уникальный marker лидера;
- различимые силуэты/цветовые группы ролей;
- shape-coded enemy telegraphs;
- priority target marker;
- command target/anchor marker;
- ключевые companion intent cues;
- incapacitated state;
- edge indicator для критичной угрозы/спутника вне кадра, если такая ситуация допустима.

### 12.4. Бюджет внимания

- Не более одного доминирующего alert одного типа одновременно; конфликтующие сигналы агрегируются или приоритизируются.
- Damage numbers необязательны; если мешают ролям/телеграфам, отключаются.
- Floating text не объясняет AI вместо визуального поведения.
- Реплика не является единственным критическим сигналом.
- Proxy VFX различают функцию формой/ритмом, а не только цветом.
- Текст читается на выбранном минимальном экране без предположения о desktop resolution.

## 13. Победа, поражение, restart и mobile interruption

### 13.1. Победа

Победа наступает, когда:

- завершена финальная encounter phase;
- все обязательные активные угрозы разрешены;
- лидер жив;
- отсутствует незавершённое критическое действие, способное нанести урон после результата.

Result summary показывает:

- outcome и длительность;
- variant;
- число команд по типам;
- состояние лидера/спутников;
- ключевые companion actions;
- основную причину полученного критического урона/defeat;
- `Replay same`, `Switch variant`, `Reset`.

Summary — test harness, не production debrief.

### 13.2. Поражение

Defeat наступает при нуле здоровья лидера.

Потеря всех спутников:

- не завершает попытку автоматически;
- оставляет лидера без их функций;
- должна быть отражена в telemetry;
- не вводит revive или progression consequence.

Технический crash, navigation lock или невосстановимый input loss не считаются игровым поражением.

### 13.3. Restart/replay

- Reset доступен из pause и result.
- Reset восстанавливает исходный состав, здоровье, cooldowns, positions, encounter phase, seed и variant.
- Replay не требует перезапуска приложения или ручной правки сцены.
- Variant можно сменить только до старта новой измеряемой попытки.
- Незавершённая попытка получает outcome `abandoned/reset`, а не `failed`.
- Служебный reset не должен быть доступен случайным нажатием в blind HUD.

### 13.4. Pause и focus loss

При ручной pause, сворачивании или потере focus:

- gameplay time, AI, hazards, cooldowns и command windows замораживаются согласованно;
- состояние попытки не продвигается в фоне;
- событие pause/resume логируется;
- после возврата показывается короткий безопасный resume countdown;
- input buffers очищаются, чтобы старое касание не вызвало действие;
- камера и HUD восстанавливают актуальное состояние;
- pause не лечит, не сбрасывает threat и не изменяет seed.

**[P]** Если процесс уничтожен ОС, попытка может считаться технически прерванной без восстановления. Полноценная session persistence отложена.

## 14. Test harness и локальная telemetry

### 14.1. Test harness

Служебный контур должен позволять без изменения контента:

- выбрать A/B;
- выбрать frozen tuning profile и encounter seed;
- начать попытку;
- reset/replay;
- скрыть служебные элементы от участника;
- показать observer summary;
- экспортировать локальный session log;
- связать telemetry, observation notes и interview анонимным participant ID;
- пометить попытку invalid с причиной;
- записать build/device/config.

Test harness не становится production menu framework.

### 14.2. Формат хранения

**[P]** События сохраняются локально в последовательном машиночитаемом формате, пригодном для экспорта и проверки порядка, например JSON Lines.

Требования:

- monotonic session time;
- UTC timestamp только для связи файлов;
- append/flush без заметного влияния на frame time;
- schema version;
- отсутствие персональных данных;
- стабильные event/enum names между frozen builds;
- явная отметка пропущенных/повреждённых данных.

### 14.3. Общий envelope события

Каждое событие содержит:

| Поле | Смысл |
| --- | --- |
| `schema_version` | Версия продуктовой схемы |
| `event_name` | Стабильное имя события |
| `session_id` | Анонимный ID измеряемой попытки |
| `participant_id` | Анонимный ID участника |
| `sequence` | Порядковый номер |
| `session_time_ms` | Время активной сессии без pause |
| `build_id` | Идентификатор сборки |
| `variant` | `A_Rally` / `B_Context` |
| `config_id` | Frozen tuning profile |
| `encounter_id` / `seed` | Содержание попытки |
| `device_id_profile` | Модель/OS/resolution/performance tier без личного device ID |

### 14.4. Обязательные события

| Событие | Обязательные данные |
| --- | --- |
| `session_started` | build, variant, config, encounter, seed, composition, device |
| `session_ended` | outcome, duration, valid/invalid, invalid_reason |
| `encounter_phase_started/completed` | phase, active actors, duration, transition_reason |
| `input_action` | action, touch/editor source, accepted/rejected, reject_reason |
| `priority_target_changed` | previous, next, input/auto reason |
| `leader_basic_attack` | target, started/resolved/cancelled, result |
| `leader_dodge_used` | direction, threat_context, avoided_damage proxy, result |
| `leader_ability_used` | target/context, result, affected actors |
| `squad_command_previewed` | predicted intent, target/context |
| `squad_command_issued` | variant, command, target/anchor, squad snapshot, cooldown state |
| `companion_command_response` | companion, role, accepted, latency, action, override/decline reason |
| `companion_intent_started` | companion, role, intent, trigger, target |
| `companion_key_action` | companion, role, action, trigger, target, result |
| `damage_applied` | receiver, source, action, amount, telegraph_id, avoidable tag |
| `actor_incapacitated` | actor, source, action, recent command/context |
| `threat_telegraph_started/resolved` | threat, source, area/type, hit/avoided outcome |
| `pause/resume` | reason, game state, duration, recovery result |
| `reset_requested` | phase, reason, resulting seed/config |
| `performance_sample` | phase, fps/frame time, memory, GC allocation sample, thermal state if available |
| `error_or_recovery` | error type, state, recoverable, recovery action |

`telegraph_seen` нельзя объявлять фактом только потому, что телеграф был на экране. Видимость — технический proxy; фактическое понимание подтверждается наблюдением/interview.

### 14.5. Damage и failure attribution

Для критического урона и defeat восстанавливается цепочка:

> threat telegraph → player/AI intent → command context → action resolution → damage → incapacitation/defeat

Автоматическая telemetry фиксирует факты, но не решает, считал ли игрок ситуацию справедливой. Наблюдатель отдельно кодирует:

- `player_decision`;
- `readable_enemy_threat`;
- `companion_behavior`;
- `input/usability`;
- `camera/readability`;
- `technical_failure`;
- `unclear`.

### 14.6. Performance data

Собираются:

- frame time/fps samples по encounter phase;
- worst-case spike context;
- memory trend;
- GC allocation samples;
- actor/effect count;
- pause/resume recovery;
- device, OS, resolution, quality profile и thermal context.

Telemetry не заменяет Unity Profiler и device profiling.

## 15. Playtest protocol и decision gates

### 15.1. Этап 1 — internal usability

Цель — убрать blockers, не доказывать product hypothesis.

Проверить:

- запуск/reset/replay;
- touch zones и ложные нажатия;
- movement/target/dodge/ability;
- command preview и acknowledgement;
- camera и потери объектов из кадра;
- понятность ролей без устного объяснения;
- отсутствие критических AI/navigation ошибок;
- целостность telemetry;
- pause/focus recovery;
- базовую производительность на Android proxy/target.

Разработчики и знакомые с GDD не входят во внешнюю выборку.

### 15.2. Этап 2 — counterbalanced comparative A/B

**Выборка:** 15 внешних целевых участников как рабочий minimum из `ProductValidationPlan.md`.

Протокол:

1. Получить согласие, назначить anonymous participant ID, записать device familiarity.
2. Не объяснять fantasy «лидера живого отряда» и различия вариантов.
3. Дать только минимальную системную инструкцию запуска.
4. При необходимости провести короткую неметрическую input calibration без команд.
5. Участники делятся на сбалансированные последовательности `A→B` и `B→A`.
6. Оба прогона используют одинаковый content/config; допустимые seeds распределяются симметрично.
7. Между прогонами не объяснять ошибки и не подсказывать, что должен делать вариант.
8. После каждого прогона собрать краткое открытое воспроизведение.
9. После обоих — сравнительное интервью и replay-intent.
10. Observer notes, telemetry и интервью связываются по participant ID.

Learning effect анализируется по порядку прохождения. Если второй вариант стабильно выигрывает независимо от identity, тест не выбирает control model и требует нового дизайна протокола.

### 15.3. Blind-вопросы

Сначала открытые, без терминологии GDD:

- Кем вы были в этой игре?
- Что было главным в бою?
- Что вы контролировали напрямую, а что происходило само?
- Чем отличались участники вашей команды?
- Вспомните момент, когда спутник помог или помешал.
- Что произошло после вашей команды?
- Когда вы чувствовали влияние на исход?
- Что было несправедливо или непонятно?
- Почему вы выбрали одну цель вместо другой?
- Какой из двух способов командования вы предпочли и почему?
- Что бы вы изменили в составе при повторе?
- Хотели бы вы сыграть ещё раз прямо сейчас? Ради чего?

### 15.4. Наблюдения

Наблюдатель фиксирует:

- время до уверенного движения;
- потерю лидера/цели/спутника из вида;
- ложные нажатия;
- игнорирование command control;
- ошибочное ожидание от preview;
- реакцию на самостоятельное действие спутника;
- взгляд на HUD вместо поля;
- физическую нагрузку и положение пальцев;
- попытки микроконтролировать спутников;
- моменты обвинения AI;
- объяснимость ключевого урона/defeat;
- разницу первого и второго прогона.

### 15.5. Рабочие пороги Stage 0

Для 15 внешних целевых участников:

| Сигнал | Порог |
| --- | ---: |
| Освоили базовое управление без устной помощи | не менее 12 из 15 |
| Своими словами объяснили влияние на отряд | не менее 10 из 15 |
| Различили функции трёх спутников | не менее 10 из 15 |
| Вспомнили конкретное полезное автономное действие | не менее 10 из 15 |
| Выразили сильное намерение повторить с другим составом | не менее 9 из 15 |
| Обвинили несправедливый AI в ключевом провале | не более 3 из 15 |

Порог понимания push-your-luck из общего Validation Plan **не применяется**, поскольку risk/return отсутствует в Stage 0.

### 15.6. Выбор control variant

Вариант может быть рекомендован, если одновременно:

- проходит центральные пороги;
- лучше объясняется участниками без подсказки;
- даёт наблюдаемое влияние, а не только более высокий damage;
- не ухудшает unfair-AI attribution;
- не создаёт неприемлемую touch/workload нагрузку;
- преимущество сохраняется после учёта порядка A/B;
- техническая стоимость и количество исключений не непропорциональны ценности.

Если данные разделены, фиксируется третья проверяемая модель или следующий самый дешёвый различающий тест. Нельзя объявлять Rally победителем только потому, что он соответствует текущему vision, либо Context победителем только из-за большей функциональности.

### 15.7. Решения по gate

| Решение | Условия |
| --- | --- |
| `proceed` | Центральные product thresholds и feasibility gate пройдены; выбран variant или определён ограниченный финальный confirmation test |
| `iterate` | Fantasy заметна, но конкретный input, feedback, tuning, camera или encounter мешает валидной оценке |
| `reduce scope` | Core работает, но третий спутник, третий контекст или часть presentation создаёт непропорциональный долг |
| `pivot` | Лидерство/доверие не возникают в обоих вариантах, но сильная часть — например, автономные роли — подтверждена |
| `stop` | После валидных итераций центральная гипотеза не работает либо требуемая читаемость/performance недостижима в допустимом scope |

Пороги directional, а не статистическое доказательство retention. Решение принимает совокупность поведения, объяснений, telemetry, feasibility и качества теста.

## 16. Технические дизайн-ограничения

Этот раздел задаёт ограничения будущему technical design, но не предписывает классы.

### 16.0. Текущий baseline проекта

Ненормативный срез на дату версии GDD:

- проект использует Unity `6000.7.0a3`;
- `GameBootstrapper` является единственной текущей Unity-точкой входа и создаёт `ApplicationRoot`;
- `ApplicationRoot` владеет application-lifetime LightDI container и logger, а gameplay state в нём отсутствует;
- в `Assets/Game` существуют только `Bootstrap` и `Architecture/Composition`;
- текущие game assemblies — `Game.Bootstrap` и `Game.Architecture.Composition`;
- отдельного `SquadCombat` module, его сцен, prefabs, input actions и тестов пока нет;
- установлены используемые архитектурным направлением Root, Disposable, LightDI, MVP/MVVM, Config и UniTask, а также Unity Input System и AI Navigation.

Baseline нужен для отдельного technical design и должен быть перепроверен перед реализацией. Он не превращает установленные пакеты в обязательные решения там, где у Stage 0 нет реальной потребности.

### 16.1. Ownership и lifecycle

- `Bootstrap` остаётся единственной Unity-точкой входа.
- Application-lifetime services создаются в application composition root.
- Combat encounter принадлежит отдельному feature/scene scope, а не `ApplicationRoot`.
- `SquadCombat` FeatureRoot создаёт и владеет своим object graph, состоянием, subscriptions, runtime resources и cancellation.
- Создавший объект освобождает его ровно один раз.
- При завершении попытки сначала останавливаются input/async/tick sources, затем feature objects, затем scene bindings.
- Pause — изменение состояния активного feature, а не уничтожение application scope.
- Любая операция, способная пережить frame, имеет owner token, completion/error boundary и stop path.
- Fire-and-forget допустим только на явной границе с логированием ошибок.

### 16.2. Чистые правила и Unity adapters

Без `MonoBehaviour`, `Transform`, `GameObject`, static Unity state и scene data должны быть проверяемы, где это содержательно:

- target validity/scoring;
- combat state transitions;
- damage resolution;
- command intent и context resolution;
- companion decision priorities;
- cooldown/active-window rules;
- victory/defeat;
- telemetry mapping;
- deterministic encounter phase rules.

Unity adapters отвечают за:

- touch Input System;
- movement/physics/navigation bindings;
- camera;
- animation, VFX, audio и haptics;
- prefab/scene references;
- frame sampling и focus callbacks.

Domain не зависит от Unity, DI, UI, Config API, telemetry storage или конкретной scene.

### 16.3. Presentation

- Gameplay presentation использует MVP.
- View принимает Unity events и отображает состояние; combat rules не живут во View.
- Presenter связывает Model/View, но не становится global manager или Unity lifecycle hub.
- HUD, если оформляется как UI screen/state, следует MVVM-границе; ViewModel не содержит world combat rules.
- Создание и initialize/dispose presenter выполняет FeatureRoot/factory с одним выбранным sync/async path.

### 16.4. Dependency direction

Разрешённое направление:

```text
Bootstrap / Application Composition
                ↓
SquadCombat Composition
                ↓
Presentation / Unity adapters
                ↓
Application
                ↓
Domain
```

Infrastructure реализует контракты, объявленные выше по смыслу владения. Обратные ссылки, service locator и доступ Domain к Unity запрещены.

### 16.5. DI и создание объектов

- Зависимости передаются constructor injection.
- `DiContainerProvider.Resolve<T>()` не используется в feature.
- LightDI применяется только при реальном module/application scope и нескольких конкретных сервисах.
- Для небольшого или повторно создаваемого encounter graph предпочтительны явные конструкторы/factory.
- Global container не владеет временными combat objects.
- Local container не вводится без отдельного technical design, учитывающего его assembly scope и пересоздание feature.
- Root не используется как DI container, singleton или update loop.

### 16.6. Configuration и data seams

Сменными данными должны быть:

- camera tuning;
- leader movement/attack/dodge/ability tuning;
- companion role/action/decision thresholds;
- command cooldown/window/radius/context rules;
- enemy health/action/telegraph tuning;
- encounter phases/spawns;
- readability/VFX intensity;
- performance sample cadence.

Правила:

- frozen test profile immutable в рамках попытки;
- config ID попадает в telemetry;
- runtime не читает tuning из global static state;
- test harness выбирает profile до создания encounter;
- если используется установленный `Config`, он инициализируется до game flow, а typed page передаётся через composition/use case после успешной инициализации;
- не создаётся универсальный remote-config pipeline для Stage 0.

### 16.7. Testability

- Pure rules получают deterministic inputs и не читают `Time`, random или scene state напрямую.
- Random/seed, clock и navigation observations передаются через конкретные boundary data только там, где они реально нужны.
- Тесты утверждают внешнее поведение, а не внутренний порядок методов.
- Lifecycle tests проверяют cancel, unsubscribe и exactly-once disposal.
- Не создаются интерфейсы вокруг маленького scene-bound кода только ради mock.

### 16.8. Запрещённые решения

- global combat/input/AI managers;
- service locator;
- scene-wide mutable singleton state;
- feature logic в `Bootstrap`/`ApplicationRoot`;
- одна универсальная state machine для всех будущих сущностей без текущих потребителей;
- reflection-heavy auto-registration;
- скрытые fallbacks, маскирующие invalid state;
- специальные ветки `if variant A/B` внутри каждого спутника/врага вместо общего command intent boundary;
- speculative status, inventory, save, backend или Addressables abstraction;
- pooling до измеренного repeated lifecycle;
- отдельный `Update` на каждом actor без обоснования и profiling.

## 17. Feature responsibility и потенциальная структура

### 17.1. Responsibility

Потенциальная feature `SquadCombat` отвечает за:

- одну активную combat attempt;
- правила лидера, отряда, команд и врагов;
- encounter state/outcome;
- предоставление наблюдаемых combat events;
- gameplay/HUD presentation этой попытки;
- создание и освобождение feature-lifetime объектов.

Не отвечает за:

- application bootstrap;
- navigation между будущими game modes;
- dungeon/expedition;
- roster/meta/economy;
- persistence/backend;
- production analytics platform;
- общую библиотеку «всех боёв».

### 17.2. Публичный контракт по смыслу

Будущий technical design должен минимально определить:

- входные данные запуска попытки: variant, tuning, composition, encounter, seed, device/test context;
- входные player intents;
- входные lifecycle events: start, pause, resume, stop/reset;
- выходные observable events: target, command, action, damage, state, outcome, performance;
- финальный attempt result;
- ownership и cancellation.

Названия типов и API здесь не фиксируются.

### 17.3. Потенциальная структура

Только после отдельного technical design и появления реального кода:

```text
Assets/Game/Features/SquadCombat/
  Domain/
    # combat values, rules, decisions, states; без Unity
  Application/
    # use cases, intents, orchestration contracts
  Presentation/
    Gameplay/
      # MVP presenters, models and Unity views/adapters
    UI/
      # HUD MVVM только при реальной необходимости
  Composition/
    # SquadCombatRoot/context/factory and explicit wiring
```

`Infrastructure/` добавляется только при появлении конкретного внешнего adapter, которым feature действительно владеет.

### 17.4. Asmdef

- Папки и asmdef не создаются заранее.
- Asmdef появляются вместе с реальным кодом после отдельного проектирования ответственности и consumers.
- Минимально возможное направление: `Composition/Presentation → Application → Domain`.
- Нельзя создавать assembly на каждый тип/папку.
- Нельзя решать cycle через dumping-ground `Shared`.
- Изменение asmdef требует compile всех затронутых assemblies.

Текущий проект содержит только `Game.Bootstrap` и `Game.Architecture.Composition`; готового `SquadCombat` module нет.

## 18. Runtime constraints

### 18.1. Target device

До финального blind comparative test обязательно фиксируются:

- модель Android device;
- SoC/RAM;
- OS;
- resolution/render scale;
- quality profile;
- минимальный физический размер экрана;
- thermal/battery условия теста.

`Работает на телефоне команды` не является критерием.

### 18.2. Performance target

**[H]** Ориентир Stage 0 — устойчивые **30 FPS** в репрезентативном worst-case encounter на выбранном target device.

Отчёт отдельно показывает:

- обычный frame time;
- worst spikes;
- длительные просадки, мешающие dodge/telegraph reading;
- memory trend;
- GC allocations;
- thermal degradation;
- pause/resume behavior.

Точные percentile budgets и допустимая длительность spike фиксируются после выбора device и baseline profiling.

### 18.3. Runtime quality rules

- Горячие frame/tick paths не используют необязательные LINQ, closures, boxing и string formatting.
- Не выполняются повторные `Find`, hierarchy traversal и component lookup в hot path.
- UI не перестраивается каждый frame без изменения данных.
- Actor count, telegraphs и effects ограничены readability, а не только GPU budget.
- `Update`/tick имеет конкретную непрерывную обязанность и владельца.
- Логирование/telemetry не создаёт заметных spikes.
- Повторный instantiate/destroy измеряется до решения о pooling.
- Pooling вводится только при доказанном hotspot/repeated lifecycle и с явным owner/release.
- Performance claims подтверждаются Profiler/device data, а не только code review.

## 19. Матрица проверок

| Уровень | Что проверяется | Минимальное доказательство |
| --- | --- | --- |
| EditMode / pure C# | target rules, command/context resolution, AI priorities, damage/state/outcome, deterministic phases, telemetry mapping | Focused behavior tests с граничными случаями |
| Lifecycle tests | start/stop/reset, cancellation, subscriptions, exactly-once disposal, pause state | Focused tests + compile |
| Compile | public contracts, asmdef direction, package references | Compile всех затронутых assemblies |
| PlayMode | связка Model/Presenter/View, spawn/despawn, encounter transitions | Focused PlayMode tests там, где они дают стабильное доказательство |
| Manual Unity smoke | touch input, camera, NavMesh, prefab/scene wiring, animation/VFX/audio, focus callbacks | Чек-лист на frozen build |
| Android proof | install/start/full encounter/reset/A↔B/pause/resume на target device | Записанный device run |
| Profiler | worst-case frame time, allocations, Unity API costs, memory trend | Unity Profiler/device capture |
| Product test | понимание, влияние, роли, trust, comparative A/B | Counterbalanced external blind test |

Зелёная компиляция не доказывает scene wiring, touch ergonomics, lifecycle или performance.

### 19.1. Обязательные граничные сценарии

- target умирает между command input и role response;
- actor/target становится unreachable;
- спутник incapacitated во время команды;
- emergency override активной команды;
- одновременные lethal damage и victory trigger;
- reset во время active telegraph/command;
- pause/focus loss во время dodge, ability и command window;
- rapid context changes для Variant B;
- leader/companion временно вне camera;
- navigation recovery;
- telemetry write failure;
- низкий frame rate не удваивает action resolution.

## 20. Порядок разработки: playable milestones

Каждый milestone заканчивается playable build или доказательством поведения; следующий не скрывает blocker предыдущего.

### M0. Test shell

Результат:

- одна запускаемая arena;
- feature lifecycle boundary;
- build/config/seed identity;
- reset;
- пустой telemetry session.

Не входят combat framework и content tools.

### M1. Лидер

Результат:

- touch movement;
- camera 3/4;
- target selection;
- auto basic attack;
- dodge;
- active ability;
- одна неподвижная/простая test target;
- базовые EditMode rules и Android input smoke.

Exit: управление не требует desktop-only преимуществ.

### M2. Базовая угроза

Результат:

- pressure enemy;
- telegraphed attack;
- damage/health/defeat;
- читаемая контригра;
- deterministic restart.

Exit: игрок может объяснить источник урона.

### M3. Один спутник

Результат:

- одна автономная роль;
- intent/action/result telegraph;
- formation distance;
- ключевое действие и telemetry.

Exit: спутник полезен без команды и не требует микроконтроля.

### M4. Три роли

Результат:

- protector;
- damage/debuffer;
- support/controller;
- role priorities/conflicts;
- incapacity;
- worst-case readability baseline.

Exit: роли различимы и не конфликтуют системно.

### M5. A/B commands

Результат:

- общий command intent boundary;
- Rally;
- Context Command;
- равный feedback/power budget;
- edge cases;
- frozen tuning profiles.

Exit: оба варианта playable на одном content без специальных сценовых веток.

### M6. Encounter, feedback и telemetry

Результат:

- полный 3–5 minute encounter;
- все фазы угроз;
- HUD/readability pass;
- command/action/damage/failure telemetry;
- performance samples;
- observer summary/export.

Exit: сессия воспроизводима и данные восстанавливают ключевую последовательность.

### M7. Internal test

Результат:

- устранены blockers;
- проверены A/B order, reset, pause/resume;
- зафиксированы build/config/device/known issues;
- проведён profiler pass;
- готов blind protocol.

### M8. External blind comparative test

Результат:

- 15 валидных участников;
- counterbalanced A/B;
- telemetry, observations, interviews;
- invalid sessions отделены;
- пороги рассчитаны без изменения задним числом.

Недобор документируется, но не считается завершением external gate и не позволяет принять `proceed`.

### M9. Decision report

Результат:

- `proceed / iterate / reduce scope / pivot / stop`;
- выбранный control direction либо следующий дешёвый тест;
- feasibility findings;
- изменения продуктовых документов;
- scope Stage 1 не утверждается автоматически.

## 21. Риски, edge cases и открытые решения

### 21.1. Основные риски

| Риск | Ранний сигнал | Ответ Stage 0 |
| --- | --- | --- |
| Бой воспринимается как autoplay | Игрок только удерживает joystick | Усилить пространственные угрозы/target decisions; не добавлять кнопки автоматически |
| AI воспринимается несправедливым | Команды игнорируются, причина не видна | Исправить priority/telegraphing; отделить bug от модели автономности |
| Три спутника не читаются | Роли/лидер теряются на экране | Снизить VFX/actor density; проверить scope reduction до двух |
| Rally выглядит как обычная ability | Игрок не связывает реакции ролей с leadership | Усилить общую причинность и role-specific response |
| Context решает бой сам | Иконка/auto-context заменяет решение игрока | Упростить resolver или изменить input, не усиливая скрытую автоматизацию |
| A/B сравнение нечестно | Один variant имеет больше power/polish | Вернуться к общему budget и повторить frozen test |
| Encounter проверяет DPS | Команда не меняет решение/outcome | Добавить competing priorities, не больше health |
| Camera скрывает угрозы | Урон приходит из-за кадра | Настроить framing/edge signals; не добавлять rotation без теста |
| Proxy art искажает вывод | Действие не читается из-за placeholder | Довести функциональную presentation до минимального parity |
| Navigation требует исключений | Спутники teleport/застревают | Упростить arena/positions; не строить универсальный pathing workaround |
| Telemetry влияет на runtime | Spikes/allocations при событиях | Batch/format iteration и profiler; сохранить локальный scope |
| Target device слишком поздно выбран | Editor/мощный телефон скрывает проблемы | Выбрать device до freeze внешнего теста |

### 21.2. Открытые решения

Следующие неизвестные должны быть закрыты данными или оставлены помеченными:

| Решение | Когда закрыть | Метод |
| --- | --- | --- |
| Target Android device и минимальный экран | До M7 | Product/technical constraint |
| Camera angle, distance, smoothing, offset | До frozen comparative build | Internal device usability |
| Touch target-selection gesture | До M5 | Internal A/B usability, одинаково для variants |
| Dodge window/cooldown/fallback direction | До M7 | Readability и fairness tuning |
| Точная active ability | До M4 | Пространственное решение без конкуренции с command |
| Basic attack range/cadence/cancel | До M7 | Passive-play и responsiveness observation |
| Companion role proxy abilities | До M4 | Role readability test |
| Formation distance и emergency override | До M7 | Trust/navigation observation |
| Command cooldown/window/radius | До M7 | Equal-budget tuning |
| Context B: три или два контекста | До M5 freeze | Touch comprehension |
| Arena geometry и enemy counts | До M6 | Decision density + profiler |
| Exact encounter seeds | До M7 | Reproducibility и counterbalance |
| Audio/haptic intensity | До M7 | Readability на device |
| Performance percentiles/spike budget | После device baseline, до external test | Profiler |
| Recruitment profile и A/B allocation | До внешнего теста | Research protocol |

Число, не подтверждённое тестом, не должно появляться как production guarantee.

### 21.3. Change-control triggers

Новая версия GDD обязательна, если меняются:

- центральная гипотеза;
- party size;
- direct-control model;
- auto attack contract;
- состав A/B;
- command input budget;
- encounter purpose;
- external thresholds/protocol;
- owner/lifecycle boundary;
- in-scope/non-goals.

Обычный tuning внутри заранее объявленных диапазонов фиксируется новым `config_id`, но не требует новой версии GDD до freeze.

## 22. Definition of Done и decision report

### 22.1. Definition of Done Stage 0 artifact

Stage 0 как проверка завершён, когда:

- существует playable Android build с одним полным 3–5 minute encounter;
- лидер имеет все in-scope действия;
- три proxy-роли автономны, различимы и телеграфированы;
- оба control variants работают на одном content и общем power/input budget;
- есть victory, defeat, reset, replay, variant select и pause/focus recovery;
- telemetry schema собирает полную последовательность команды, role response, damage/failure и performance;
- build/config/device/seed/known issues зафиксированы;
- выполнены релевантные automated/compile/manual/device/profiler проверки;
- internal blockers устранены или явно исключают внешний тест;
- проведён валидный counterbalanced blind comparative test;
- результаты сопоставлены с порогами `ProductValidationPlan.md`;
- выпущен decision report;
- связанные product docs обновлены только если решение действительно меняет direction.

Stage 0 может быть **завершён с отрицательным результатом**. `Done` означает валидное знание и решение, а не обязательный `proceed`.

### 22.2. Feasibility gate

Для `proceed` дополнительно требуется:

- читаемость на минимальном выбранном экране;
- производительность близка к 30 FPS target в worst-case encounter;
- нет архитектурной зависимости от сценовых ручных исключений;
- AI/feedback расширяются через данные и ясные responsibilities;
- стоимость создания следующего спутника/врага/encounter можно оценить;
- camera/control/party model остаются заменяемыми без переписывания Domain всего продукта.

### 22.3. Формат decision report

1. **Hypothesis и build:** версия GDD, build/config/variant/seed.
2. **Sample:** участники, критерии, A/B order, устройства, исключённые сессии.
3. **Known limitations:** дефекты и ограничения валидности.
4. **Observed behavior:** onboarding, input, decisions, role recognition, trust.
5. **Quantitative signals:** пороги, command use, response, outcome, damage/failure attribution.
6. **Qualitative evidence:** повторяющиеся объяснения и контрпримеры.
7. **A/B comparison:** влияние порядка, preference, workload, fairness, technical cost.
8. **Readability/performance:** экран, camera, profiler/device findings.
9. **Confirmed / rejected / unknown:** отдельно для каждого вопроса раздела 2.3.
10. **Decision:** `proceed / iterate / reduce scope / pivot / stop`.
11. **Control direction:** выбранный variant, третья модель или причина отсутствия выбора.
12. **Next cheapest test:** одна следующая неопределённость и критерий.
13. **Stage 1 implications:** только разрешённые выводы; не production scope.
14. **Document changes:** какие product/GDD/technical документы нужно обновить.

### 22.4. Финальный scope check

Перед утверждением отчёта команда отвечает:

- Каждый ли реализованный элемент поддержал центральную гипотезу?
- Не было ли результата, созданного scripted showcase вместо системного поведения?
- Не подменили ли proxy product contract?
- Не зафиксированы ли Stage 1+ решения без данных?
- Можно ли дешёво заменить проигравший camera/control/party вариант?
- Стабильны ли responsibilities и event/data seams?
- Удалены ли лишние abstractions, managers и content?
- Можно ли по данным объяснить, почему принято именно это решение?

Если ответ «нет», Stage 0 не готов к решению, даже если билд формально проходим.
