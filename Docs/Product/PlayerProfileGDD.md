## 1. Назначение

Player Profile — постоянное состояние игрока между экспедициями и его представление в Guild Hall. Профиль отвечает на вопросы:

- кто является главным героем, которым игрок управляет;
- кто входит в его текущую команду;
- какие герои доступны и каковы их текущие характеристики;
- какие навыки и экипировка назначены выбранному герою;
- сколько у гильдии Gold и какой у неё ранг;
- что должно пережить перезапуск приложения.

Профиль не является универсальным контейнером всех будущих систем. Квесты имеют отдельного владельца, отдельное состояние и отдельный save contract.

## 2. Место в Guild Hall

Профиль открывается через существующую стойку регистрации. Новая обязательная физическая точка и новый обход хаба не добавляются.

Если у стойки есть непросмотренный итог экспедиции, сначала показывается итог. После его закрытия следующее взаимодействие со стойкой открывает профиль. Открытый экран блокирует перемещение по залу и возвращает управление после закрытия.

## 3. UX главного героя и команды

Разница между главным героем и спутниками не кодируется только цветом.

- Главный герой всегда находится в отдельном крупном блоке с явной подписью `Главный герой` и пояснением `Вы управляете этим героем`.
- Спутники находятся в отдельном блоке `Команда` и имеют одинаковый вторичный визуальный вес.
- Остальные доступные герои, когда они появятся, находятся в блоке `Другие герои`, а не смешиваются с активной командой.
- В списках используются стабильные hero IDs; главный герой не определяется как «первый элемент массива».
- Выбор карточки открывает детали конкретного героя, но не меняет его роль скрыто.

Минимальная компоновка:

```text
┌ Профиль гильдии ───────────── Gold ───── Ранг ┐
│ Главный герой        │ Команда                │
│ [крупная карточка]   │ [спутник] [спутник]…  │
├──────────────────────┴────────────────────────┤
│ Доступные герои      │ Детали выбранного      │
│ [список]             │ характеристики/навыки │
└──────────────────────┴────────────────────────┘
```

## 4. Данные героя

Профиль хранит только player-owned состояние и стабильные ID. Статические определения остаются в существующих catalogs.

Для героя в постоянном состоянии нужны:

- `actorId`;
- заработанный уровень;
- выбранный `loadoutId`;
- позднее — ссылки на реально существующие equipped item IDs.

Экран разрешает ID через актуальные определения и показывает:

- имя;
- уровень;
- максимальное здоровье;
- скорость перемещения;
- фактические слоты навыков, их имена и уровень;
- экипировку после появления реальной item/equipment системы.

PP-1 не создаёт пустые equipment slots и не показывает фиктивные предметы. Экипировка добавляется только вместе с предметами, правилами надевания и реальным влиянием на героя.

## 5. Состав

Постоянный состав представлен явно:

- один `leaderActorId`;
- упорядоченный список `companionActorIds`;
- все ID обязаны принадлежать roster;
- один герой не может одновременно занимать две позиции;
- допустимый размер активной группы определяется текущим setup/config, а не числом в UI или тесте.

PP-1 только отображает текущий состав, созданный из production default при первом запуске. PP-2 позволяет менять лидера, спутников и loadout, сохраняет выбор и использует его при следующем Dungeon Run.

## 6. Деньги

- Единственная spendable-валюта текущего направления — Gold.
- Баланс неотрицателен и принадлежит постоянному профилю.
- PP-1 создаёт, сохраняет, загружает и отображает баланс.
- PP-1 не начисляет текущие `RewardGrant` и не реализует продажу.
- Применение результата и продажа появляются только как конкретные идемпотентные use cases; View не меняет баланс напрямую.

Кристаллы монстров и другие продаваемые находки не становятся второй валютой автоматически. После появления inventory они являются предметами/ресурсами, которые стойка может продать за Gold.

## 7. Ранг

Ранг относится к профилю гильдии/авантюриста, а не заменяет уровень конкретного героя.

- PP-1 поддерживает отсутствие присвоенного ранга и показывает `Ранг: —`.
- Стабильный `rankId`, definitions, лестница рангов, требования и стоимость повышения вводятся в PP-5 после отдельного продуктового решения.
- Повышение выполняется у стойки регистрации и только через профильный use case.
- Доска позже получает уже рассчитанную доступность предложения; она не читает rank state и не проверяет правила сама.

## 8. Сохранения

PP-1 сохраняет одним versioned profile record:

- Gold;
- optional `rankId`;
- roster героев с уровнем и loadout ID;
- отдельный `leaderActorId`;
- ordered companion IDs.

Новый профиль создаётся из текущего production default состава. Профиль загружается и валидируется до показа Guild Hall. Unity objects, View state, config assets, Addressables keys/handles и состояние открытого окна не сохраняются.

Добавление equipment/inventory выполняется новой версией и миграцией. Пустые поля «на будущее» в PP-1 не резервируются.

## 9. Квесты

Квестовая система полностью вне scope Player Profile:

- свои definitions и правила;
- своё runtime/application состояние;
- свой `SaveKey<T>` и миграции;
- профиль может отдавать quest-системе только необходимые read-only факты через узкий контракт;
- quest state не помещается в profile DTO и не управляется Profile UI.

## 10. Milestone PP-1

Первый законченный срез:

1. При первом запуске создаётся валидный профиль из текущего default team setup.
2. Профиль записывается через SaveStore V2 и загружается при следующем запуске.
3. Стойка регистрации открывает read-only Profile screen, если session summary уже отсутствует или был закрыт.
4. Экран показывает Gold, `Ранг: —`, главного героя, всех спутников и детали выбранного героя.
5. Главный герой визуально и текстово отличается от команды независимо от цвета.
6. Характеристики и навыки соответствуют текущим Actor/Skill definitions и выбранному loadout.
7. Количество героев, спутников, уровней и skill slots берётся из входных данных, а не фиксируется тестом.

## 11. Non-goals PP-1

- изменение лидера, состава, уровня или loadout;
- inventory, equipment slots, предметы и stat modifiers;
- применение наград, продажа и покупка;
- rank definitions, promotion rules и contract gating;
- квесты;
- cloud/account save, несколько профилей и save-slot UI;
- универсальная progression/economy/item framework;
- изменение Dungeon Run и текущих reward contracts.

## 12. Acceptance направления

- Перезапуск восстанавливает тот же профиль без silent reset.
- UI явно разделяет главный герой / команда / прочий roster и не выводит врагов из Actor catalog.
- Показанные stats и skills соответствуют сохранённым actor/level/loadout IDs и текущим definitions.
- Profile UI не читает SaveStore или config и не изменяет business state напрямую.
- Guild Hall получает подготовленный immutable snapshot и остаётся владельцем только presentation lifecycle.
- Неизвестный/повреждённый ID завершает загрузку наблюдаемой ошибкой; production profile не заменяется default молча.
- Тесты проверяют переданные данные и инварианты, а не фиксированное число героев, спутников или навыков.
